Binary search tree

height 0 · 0 nodes
One key per node. A new key always becomes a new leaf — the tree never reshapes itself, so a bad insertion order can make it deep and lopsided.

B-tree (order 4)

height 0 · 0 nodes
Up to 3 keys share a node. When a node would need a 4th, it splits in two and pushes its middle key up — which is how the tree grows sideways before it grows down.

What to watch for

Notice the BST's left branch: 10 → 5 → 6 → 7 forms a straight, deepening chain, because every one of those values happens to be smaller than the one before it. Nothing in a plain BST corrects for that.

In the worst case — data inserted in sorted order — a BST degrades into a straight line: a linked list wearing a tree's name, with O(n) lookups instead of O(log n).

Why the B-tree stays flat

The B-tree never lets a node overflow silently. The moment a node would hold a 4th key, it splits into two 1-key nodes and promotes the middle value — which is exactly the split you'll see happen on insert #4 and again near the end.

This is also why database indexes are B-trees rather than binary trees: predictable, shallow depth regardless of insertion order matters far more than a database can bet on data arriving in a "nice" order.
