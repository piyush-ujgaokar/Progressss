Every index is a bet about which questions you'll ask twice.

A working reference on how MongoDB indexes are structured, built, chosen, and misused — from the B-tree underneath to the query planner deciding whether to trust it.

01 — FIRST PRINCIPLES

What an index actually is

A MongoDB index is not a copy of your data. It's a small, ordered lookup structure that stores just the value of one or more fields, plus a pointer back to the full document on disk. Ask for { email: "a@x.com" } without an index, and Mongo walks every document in the collection — a COLLSCAN — checking each one in turn. With an index on email, it instead walks a sorted structure straight to the match and follows the pointer.

Think of the collection as an unsorted stack of index cards in a drawer, and the index as a second, sorted stack that only holds the one detail you search by — plus a note saying "see card #4,381." You still have one drawer of real cards. The index is the shortcut into it, and it costs a second stack to maintain.

The trade you're always making: indexes speed up reads and cost writes. Every insert, update, or delete has to update the real document and every index that field touches. An unused index is pure cost — no benefit, ongoing tax on every write.

02 — INTERNALS

Under the hood: B-trees and WiredTiger

MongoDB's default storage engine, WiredTiger, stores both collections and indexes as B-trees — specifically B+ trees, where every value lives in a leaf node and internal nodes exist purely to route a search downward. Each internal node holds a handful of sorted keys and pointers to child nodes covering the ranges between them.

A lookup starts at the root, compares your search value against the keys in that node, and follows the one pointer whose range contains it — repeating one level down until it reaches a leaf. That leaf holds the indexed value and a record id, which the engine uses to fetch the actual document from the collection's own B-tree.

Why this matters in practice

A B-tree keeps lookups fast — O(log n) — because tree depth grows very slowly as data grows; a collection with a billion documents might still only need 3–4 levels. It's also why WiredTiger wants indexes resident in RAM: every level down is, worst case, a disk page fault. An index bigger than your working set forces the engine to page from disk on every lookup, which erases most of the benefit.

Document data itself is stored the same way, keyed by an internal record id (in modern WiredTiger, roughly the _id). So an index lookup is really two B-tree walks: one through the index to find the record id, one through the collection to fetch the document — unless the index alone contains every field the query needs, which brings us to covered queries below.

03 — CATALOG

Types of indexes

Click a tab to open that card.

Single field

One field, one direction. The default and the workhorse — covers equality and range queries and sorts on that field.

db.users.createIndex({ email: 1 })

Compound

Multiple fields in one index, order matters. Follows the prefix rule: a compound index on {a, b, c} can serve queries on a, a+b, or a+b+c — but not b alone.

db.users.createIndex({ city: 1, age: -1 })

Multikey

Automatically created when you index a field that holds an array — MongoDB adds one index entry per array element. A document with a 500-item array contributes 500 entries, so array fields can bloat an index fast.

db.posts.createIndex({ tags: 1 }) // tags: ["a","b","c"]

Text

Tokenizes string content for keyword search with stemming and stopword removal. A collection may have only one text index, though it can span several fields.

db.articles.createIndex({ title: "text", body: "text" })

Hashed

Stores the hash of a field's value instead of the value itself. Distributes writes evenly, which is why it's the standard choice for a shard key — but hashes can't serve range queries, only equality.

db.events.createIndex({ userId: "hashed" })

Geospatial

2dsphere indexes GeoJSON data on a sphere (real-world coordinates); the older 2d is for flat planar coordinates. Powers $near, $geoWithin, and similar queries.

db.places.createIndex({ location: "2dsphere" })

Wildcard

Indexes every field (or every field under a path) without naming them up front — useful for unpredictable, user-defined document shapes. Costs more to maintain than a targeted index and shouldn't replace one for known hot fields.

db.logs.createIndex({ "metadata.$**": 1 })

TTL (time to live)

A single-field index on a date value that makes MongoDB automatically delete documents once they age past a threshold. A background job sweeps expired documents roughly once a minute — not instantly.

db.sessions.createIndex(
  { createdAt: 1 },
  { expireAfterSeconds: 3600 }
)

Unique

Rejects a write that would duplicate an existing indexed value. Applies per shard key range in a sharded collection, and treats a missing field the same as null — so more than one document without the field will collide.

db.users.createIndex({ email: 1 }, { unique: true })

Partial / sparse

Sparse skips documents missing the field entirely. Partial is the more flexible modern version — index only documents matching an arbitrary filter, which also fixes the unique-plus-missing-field collision above.

db.users.createIndex(
  { email: 1 },
  { unique: true, partialFilterExpression: { email: { $exists: true } } }
)

05 — DECISION MAKING

How the query planner picks an index

When a query can be served by more than one index, MongoDB doesn't guess — it runs a short competition. Each candidate index gets a limited trial execution against the real query, and whichever finishes fastest (in examined-documents terms) wins. That plan is then cached, so repeated identical queries skip the trial and go straight to the winner, until the collection's indexes or data shape change enough to invalidate the cache.

Covered queries

If every field a query needs to filter, sort, and return is present in the index itself, MongoDB never has to open the underlying document at all — the index is the answer. This is a covered query, and it's the fastest shape a read can take. Adding an unindexed field to the projection breaks the cover immediately.

Index intersection

MongoDB can, in some cases, combine two single-field indexes to answer one query instead of using neither — but a purpose-built compound index for a common query shape is almost always faster and more predictable than relying on intersection.

Rule of thumb: don't guess. Run .explain("executionStats") and check totalDocsExamined against nReturned. If they're far apart, the index isn't narrowing the search the way you think it is.

06 — WHERE IT BITES

Edge cases worth remembering

01

Every index taxes every write

Ten indexes on a collection means one insert triggers eleven structural updates. Index only what you filter, sort, or join on regularly.

02

The prefix rule is strict

A compound index on {city, age} serves city and city+age queries — not an age-only query. Field order is a design decision, not a formality.

03

Sort direction has to line up

An index built {city: 1, age: -1} may not serve a sort requesting the opposite direction on the second field efficiently.

04

Unanchored regex and $ne can't use a sorted range

/^Rah/ can use an index as a prefix scan; /ahul/ and $ne/$nin generally can't, since "everything except X" isn't a contiguous range in a sorted tree.

05

Unique indexes treat "missing" as a value

Two documents both lacking an email field collide on a unique index, because MongoDB indexes the missing field as null for both. Fix with a partial filter expression.

06

Indexes bigger than RAM get slower, not faster

WiredTiger wants the working set of indexes in memory. Once an index outgrows available RAM, lookups start paging from disk and the benefit erodes.

07

Only one text index per collection

You can't have separate text indexes on title and body — they have to be declared together in a single text index.

08

Case sensitivity is the default

"Rahul" and "rahul" are different index entries unless a collation is attached to the index to normalize case and accents.

09

Array fields multiply entries

A multikey index adds one entry per array element, per document. A handful of documents with large arrays can bloat an index disproportionately to the collection size.

10

$or often can't share one index scan

MongoDB may run a separate index scan per branch of an $or and merge the results, which is usually less efficient than a single compound index serving an equivalent $and.

11

Low-cardinality fields barely help

Indexing a field with only a few distinct values (like a boolean or a two-value status) narrows very little. Indexes pay off most on high-cardinality fields like email or a unique id.

12

A build on a large existing collection isn't free

Building an index on millions of existing documents takes real time and I/O, even as an online build. Plan index creation for low-traffic windows on large production collections.
